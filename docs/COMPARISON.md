# espacenet-cli 两版对比报告（产品级）

> **匿名化说明**：本报告为历史验收记录，文中检索式与公开号已替换为占位符/中性示例，数字保留原始量级作为证据；示例专利现为公开知识（US5960411A、EP2600908A1）。

- **旧版（A）**：`espacenet-cli/` — 手工开发的 Node.js CLI（v0.1.0）
- **新版（B）**：`espacenet-cli-anything/espacenet/agent-harness/` — 用 **HKUDS CLI-Anything**
  7 阶段流水线重新开发的 `espacenet-cli`（Python，v0.1.0）

两版面向同一真实后端（本机 Edge 常驻会话 + Espacenet 前端同款 REST 服务）。
本报告以**产品对比**为主（第一、二章），开发过程对比附后（第三章）。
产品验收证据：[ACCEPTANCE.md](ACCEPTANCE.md)——旧版真实任务在新版上重放，23/23 通过。

---

## 一、产品对比：同样的活，干得怎么样

### 1.1 数据正确性——逐条比对，完全一致

把旧版当天真实跑过的检索在新版同参数重放，与旧版留档数据逐条比对：

| 任务 | 结果 |
|------|------|
| 主检索（已匿名检索式） | 两版均为 **88 族/197 件**；197 条公开号 **Jaccard=1.000**，标题/申请人/公开日/同族号字段一致率 **788/788** |
| 中文全文词全量（已匿名检索式） | 45/45 交集，Jaccard=1.000，字段 180/180 |
| 单件核查（detail/claims/description/family/legal/pdf） | 全部成功；PDF 4MB 且魔数验证通过 |
| 错误路径（CJK+字段、多年 pd within） | 与旧版相同被 EPO 拒（HTTP 400），错误信息结构化且带建议动作 |

**判定：两版产出数据无差别**——因为共享同一套已验证的传输协议。这正是新版策略的产物：
不重造通道，把旧版验证过的协议知识作为流水线 Phase 1 的输入继承下来。

### 1.2 稳定性与限流韧性——新版更强

EPO Fair Use 是这个产品最大的现实约束。验收中真实触发了限流：

- 旧版机制：Fair-Use 403 等 5s 重试一次；持续限流只能人工等冷却（README 如此记载）。
- 新版机制：403 同款处理 **+ HTTP 429 两级退避**（30s→90s，尊重 `Retry-After`），大拉取
  页间隔 600ms。验收中大 `--all`（16 页）打满配额导致后续请求被 429，修复后同一场景
  47.7s 成功拉取 500 条。
- **判定：新版在真实恶劣网络条件下表现更稳**，且失败时报 `FAIR_USE_REJECTED` 并给出
  可执行的恢复建议，Agent 可自行决策退避重试。

### 1.3 Agent 可用性（产品核心场景）——代差

这是两版最大的产品差异。旧版是"给人用、顺便给 Agent 用"；新版按 CLI-Anything 规范
是"首先给 Agent 用"：

| 能力 | 旧版 | 新版 |
|------|------|------|
| 机器可读输出 | 部分（search 的 --json alias） | **每个命令 `--json`**，验收实测 stdout 纯 JSON、进度全部走 stderr，管道零污染 |
| 错误契约 | 自由文本 | 结构化 `[错误码]` + `→ 建议动作` + 语义化退出码（用法错误=2），Agent 可编程处理 |
| 可发现性 | 需读 README | SKILL.md 装入 Agent 技能目录，任何技能型 Agent 开箱即会 |
| 交互模式 | 单发命令 | 单发命令 + **默认 REPL**（连发探索、`save`/`context` 结果驻留、管道可用） |
| 预览安全 | — | 变更类命令 `--dry-run` |
| 安装分发 | npm link（私有） | pip 安装 / 可发布 PyPI，`cli-hub` 生态可管理 |

### 1.4 互操作与共存——两版可并肩用

- 共享同一常驻 Edge 会话（相同 endpoint 文件格式）：验收实测新版 `status` 直接读到
  旧版会话启动的 Edge（端口 61392），人机验证凭据互通，任一方 `connect` 双方受益。
- 检索记录簿目录格式相同：历史会话/报告互通，新版可读旧版 journal。
- 已知差异：新版无独立 `quit` 命令（`edge stop` 等价）；`report` 复现命令前缀为新命令名。

### 1.5 产品成熟度——旧版唯一仍有优势的维度

- 旧版经过多轮真实生产使用（今天的禧玛诺传动系统任务即是）。
- 新版首日交付，但已通过 65 项自动化测试 + **23 项真实任务验收**；验收还当场抓出
  3 个真缺陷（REPL 结果驻留、429 退避、REPL 引号分词）并全部修复回归。
  换算成风险：新版的问题暴露发生在验收阶段而非生产阶段，这正是"先测试再使用"的价值。

**产品总评**：数据能力持平（同一协议），稳定性和 Agent 可用性新版明确更强，成熟度
旧版略先。作为"AI Agent 的专利检索工具"这一产品定位，**新版是更好的产品**；旧版的
价值已沉淀为新版的协议底座，可退役为参考实现。

## 二、产品规格对比速览

| 维度 | A 旧版（手工） | B 新版（CLI-Anything） |
|------|----------------|------------------------|
| 技术栈 | Node.js ≥20，1 依赖 | Python ≥3.10，3 依赖（click/prompt-toolkit/playwright） |

| 测试 | 0 | 65（49 单元 + 6 子进程 + 10 真实后端 E2E）+ 23 项真实任务验收 |

| 代码量 | 2,134 行 + 0 测试 | 2,514 行产品码 + 567 行皮肤 + 652 行测试 |

## 三、开发过程对比（方法论）

| | A 手工开发 | B CLI-Anything 流水线 |
|---|-----------|----------------------|
| 过程 | 直接写码 → README | 7 阶段：目标分析→架构设计→实现→测试计划→测试→回填→SKILL.md→打包；全程受 HARNESS.md 硬规则约束 |
| 质量闸门 | 无（靠真实使用事后暴露） | 计划先行（TEST.md Part 1）、真实后端 E2E 强制、产物魔数验证、`_resolve_cli` 安装态子进程测试、validate 清单 83/83 |
| 缺陷暴露时机 | 使用中 | 合并前（验收又兜底抓出 3 个交互层缺陷） |
| 可复现性 | 一次性 | 流水线可对任意软件重放（本机已部署 hub + 全局 skill） |

**方法论证**：本次开发中被测试直接抓出 5 个实现缺陷（fetch 桥解构、`--json` 未注册、
`report -o` 重复注册覆写报告、REPL 无控制台崩溃、429 未处理），验收再抓出 3 个交互缺陷
（REPL 结果驻留、限流退避不足、CQL 引号剥离）——8 个问题没有一个流入生产使用。
"更科学"不是流程形式，而是缺陷左移的可量化结果。

## 四、遗留与建议

- 两版并行跑 1-2 周后，旧版可退役（新版的协议与其逐字节兼容，回滚成本为零）。
- 后续 `refine`：`description` 独立 E2E、`preview` 结果集快照、PyPI 公开发布。
- EPO Fair Use 对两版同等生效：批量 ≤2000 条、默认 pacing 700ms、连续大拉取注意冷却。
