# RATELIMIT.md — Espacenet 限流实测与效用最大化使用指南

**数据来源**：2026-09-24 晚对真实服务的阶梯实验（原始日志 `acceptance/ratelimit-*.jsonl`），
叠加当日验收/测试的多次真实限流事件。官方口径：EPO Fair Use 章程规定**单个 IP 每分钟
10 次"检索类动作"**（epo.org Fair use charter），并声明不支持机器人式自动化访问。

## 一、先说结论（怎么用最划算）

| 场景 | 推荐做法 | 依据 |
|------|----------|------|
| 交互式查几个专利 | 随便用，默认参数即可 | 桶容量约 20 次检索 |
| 连续检索浏览 | 每次间隔 **≥6 秒**（官方 10 次/分钟线） | 3s 间隔实测第 8 个就触发 |
| 批量 `--all` 拉取 | `--pacing 1000` 以上，单批 **≤200 条（约 10 页）**，批间隔 **≥2 分钟** | 桶补得很慢，恢复后 3 分钟只够 ~7 次 |
| 大任务（数百条） | 拆成多批，每批之间歇 2-5 分钟；或分几天/分时段 | 桶 ~20 容量 + 慢速回填 |
| 单件核查（detail/claims/family/legal/pdf） | 快，随便查 | 文献端点**不占检索配额**（见下） |
| 一旦 429 | **停手 6-8 分钟**，期间不要重试 | 实测恢复 5 分 18 秒 / 6 分 03 秒；限流期重试会吃到 Cloudflare 挑战页甚至把页面本身换成验证页 |

## 二、关键实测发现：限流只盯"检索"，不盯"取数据"

这是本次实验最有价值的发现。两类端点待遇完全不同：

| 端点类型 | 实测 | 结论 |
|----------|------|------|
| **search**（`/3.2/rest-services/search`） | 连发第 **20** 个触发 429；恢复后 3 分钟内 3s 间隔第 **8** 个触发 | 严格限流对象（=官方"检索类动作"） |
| **family/legal/claims/description/PDF**（文献数据端点） | **40 连发（8 秒内）全部 200**；0.5s/1s/2s 间隔阶梯、2-5s 随机抖动全部干净 | 实测未设限（至少远高于 2 次/秒） |

产品含义：**把检索次数最小化、数据获取最大化**是效用最大化的关键。CLI 的设计恰好如此：
一次 `search` 定位结果集，然后对每件专利的 claims/family/legal/pdf 深挖几乎不计成本。
注意 `detail` 内部用一次 search 反查著录数据，所以每件核查计 1 次检索。

## 三、错误形态（出现什么报错就是撞了什么）

| 报错 | 长相 | 是谁拦的 | 意味着什么 |
|------|------|----------|-----------|
| **HTTP 429 + "Just a moment..." HTML 页** | `<!DOCTYPE html>...<title>Just a moment...</title>` | **Cloudflare 边缘层**（突发保护） | 触发突发配额；CLI 报 `API_ERROR: 检索响应无法解析为 JSON（HTTP 429）`，内置两级退避（30s→90s，尊重 Retry-After——但实测该响应**无** Retry-After 头） |
| **HTTP 403 + `<error>` XML** | `<error><message>Fair Use...` | **EPO 应用层 Fair Use** | 政策性拒绝；CLI 等 5s 重试一次，仍败报 `FAIR_USE_REJECTED` + 放慢建议 |
| **HTTP 403 + HTML**（整个页面被换） | 人机验证页 | Cloudflare 把页面也挑战了 | 限流期反复戳会升级到这个形态；CLI 报 `CHALLENGE_BLOCKED`，需要人工在 Edge 窗口点一次复选框 |
| HTTP 400 | `<fault>` / JSON 解析失败 | EPO 检索语法层 | 不是限流，是检索式问题（如 CJK 组合进 ti=/abs=、`pd within` 多年列表） |

## 四、实测数据明细

**search 端点突发**：pacing=0 连发，第 1-19 个全部 200（16 秒内，单个 ~700ms），
第 20 个 429。
**search 间隔阶梯**：从限流恢复 3 分钟后，3 秒间隔第 8 个 429；2 秒间隔立即 429
（配额未回满）。单独满桶状态下未复测 3s/6s 长跑（避免消耗配额），按官方 10 次/分钟
执行是安全线。
**恢复时间**：两次独立测量 **5 分 18 秒**（22:59:49→23:05:07）与 **6 分 03 秒**
（23:08:35→23:14:38）。
**family 端点对照**：40 连发全 200；2s/1s/0.5s×12 阶梯全 200；2-5s 抖动×15 全 200。

**工作模型**（与全部观测一致的推断）：search 走令牌桶——容量约 20，回填慢
（恢复后 3 分钟仅够约 7-8 次）；一旦打空进入约 5-6 分钟罚时；文献端点不在桶内。

## 五、CLI 参数与限流的对应关系

- `--pacing <毫秒>`（默认 700）：任意两次请求（含文献端点）之间的最小间隔。交互式够用；
  批量拉取建议 1000-2000。
- `--all` 拉页间隔：内置 1.2s（实测校准值）+ pacing。
- 429 内置处理：自动等 30s→90s 重试两次，仍败报 `FAIR_USE_REJECTED` 并附冷却指引
  （不会无限重试把罚时越撞越长）。
- 批量任务的可靠姿势：`search '...' --all --limit 200 --pacing 1000` → 歇 2 分钟 →
  下一批。200 条一批约 4 分钟跑完，零限流风险。

## 六、局限说明

- 实测基于单一 IP、单日、匿名会话；EPO/Cloudflare 的阈值可能随时调整、按负载浮动，
  数字视为量级而非承诺。
- 长时间（数十分钟）连续 6s 间隔检索未做（有意避免过度消耗公共资源），"10 次/分钟"
  官方线是此时最好的依据。
- 想要真正 unlimited 的批量检索：正路是注册 EPO **OPS API**（官方开放接口，有免费配额，
  注册用户限速远高于匿名网页通道）。
